# T3 设计：蛋白结构任务（mmCIF 确定性重算）

> **这份文档的每一条事实都经过实测**（2026-09，本机）。凡未验证的一律标注。
> 目的是让实现者**不需要再做设计决策**，只要照着落地。

---

## 一、这道题问什么

**给定一份 PDB 的 mmCIF 原文，从坐标确定性地重算一组结构量，并与真值比对。**

题面里**直接给出 mmCIF 文件**（或镜像内已有），作答者提交一个 JSON，
逐项回答指定条目的结构量。

**为什么这样出题**：真值不是谁"写的"，而是**由原文算出来的**。
只要有原文，任何人都能独立复算并推翻我们 —— 这正是本项目的要求
（原则 ②：真值来自权威公开源，**绝不自算**）。

## 二、已核实的事实（实测，非推测）

### 2.1 数据入口：可用、无需凭据

```
https://files.rcsb.org/download/{PDB_ID}.cif
```

实测（三个条目，HTTP 200，以 `data_` 开头）：

| 条目 | 字节数 | sha256 前 12 位 |
|---|---|---|
| 1CRN | 69,506 | `23787562c427` |
| 4HHB | 772,198 | `2d3ca1bf21dd` |
| 6LU7 | 326,399 | `1496edb125c5` |

**无需 API key**，直接 GET 即可。体积 70 KB ~ 772 KB / 条。

### 2.2 许可：CC0-1.0（可再分发，无需署名）

原文（`research/DATA_LICENSES.md` §8.1 已记录并附 URL）：
wwPDB 政策页明示 PDB 归档数据为 **CC0 1.0 Public Domain Dedication**。
→ 可以整包进仓库、进镜像，无署名义务。

### 2.3 ⚠️ **标量字段不可靠 —— 这决定了题目只能建立在 `_atom_site` 上**

实测 8 个条目的字段存在率：

| 字段 | 存在率 | 结论 |
|---|---|---|
| `_refine.ls_R_factor_R_free` | **1/8** | ❌ **不能作为真值来源** |
| `_refine.ls_R_factor_R_work` | 4/8 | ❌ 不可靠 |
| `_refine.ls_d_res_high` | 7/8 | ⚠️ 多数有，但会缺 |
| `_exptl.method` | 8/8 | ⚠️ 是自由文本（`'X-RAY DIFFRACTION'`） |
| `_cell.length_a` | 8/8 | ✅ 但题目太浅 |
| `_atom_site.*` | **必然存在** | ✅ **唯一可靠的真值来源** |

**已实测的参考值（实现者应能复现这些数）**：

| 条目 | atom_count | hetatm_count | chain_count | CA 距离 (Å) |
|---|---|---|---|---|
| 1CRN | 327 | 0 | 1 | 3.794 |
| 4HHB | 4,384 | 395 | 4 | 3.704 |
| 6LU7 | 2,387 | 113 | 2 | 3.792 |
| 1UBQ | 602 | 58 | 1 | 3.804 |
| 2LZM | 1,309 | 118 | 1 | 3.857 |

（用 `loop_` 语义解析、按 §3 定义计算。**连跑两遍逐位相同**，已验证。）

> **设计后果**：任何"读某个标量当答案"的题都会大量出无解。
> T3 的题目**必须**建立在 `_atom_site` 的坐标与列上 ——
> 没有坐标就不构成一个结构，所以它一定在。

### 2.4 ⚠️ **mmCIF 解析必须按 `loop_` 语义，不能按 `#` 截断**

我第一版在第一个 `\n#` 处截断，结果 4HHB 报 **0 个原子**（实际 4,779）。
原因：mmCIF 里 `#` 是**列名块与数据块之间的分隔符**，在数据**之前**就出现，
于是截断后一个数据行都不剩。

**正确做法**（已用两种独立方法交叉验证一致）：

```
1. 定位 `_atom_site.` 起始行
2. 连续读取 `_atom_site.*` 列名，得到 ncols
3. 之后逐行读数据，直到遇到 `#` 或下一个 `_` 类别
4. 数据行以 `ATOM` / `HETATM` 开头
```

实测两种方法（loop_ 语义 vs 全文件计数）**8/8 一致**：

| 条目 | 原子行数 |
|---|---|
| 1CRN | 327 |
| 4HHB | 4,779 |
| 6LU7 | 2,500 |
| 1UBQ | 660 |
| 3AID | 1,912 |
| 5XNL | 98,986 |
| 1ATP | 3,070 |
| 2LZM | 1,427 |

`_atom_site` 有 **21 列**，前几列为：
`group_PDB`, `id`, `type_symbol`, `label_atom_id`, `label_alt_id`,
`label_comp_id`, `label_asym_id`, `label_entity_id`, `label_seq_id`,
`pdbx_PDB_ins_code`, `Cartn_x`, `Cartn_y`, `Cartn_z`, …

**这条警告是实测出来的，不是推测**。我特意写了两个实现去比：

| 条目 | ① `loop_` 语义 | ② 按 `#` 切块 | ③ 全文件计数（**裁判**） | ①对不对 | ②对不对 |
|---|---|---|---|---|---|
| 1CRN | 327 | 327 | 327 | ✅ | ✅ |
| 4HHB | **4,384** | **0** | 4,384 | ✅ | ❌ |
| 6LU7 | **2,387** | **0** | 2,387 | ✅ | ❌ |
| 1UBQ | 602 | 602 | 602 | ✅ | ✅ |
| 2LZM | **1,309** | **0** | 1,309 | ✅ | ❌ |

裁判 ③ **不解析结构**，只数全文件的 `ATOM`/`HETATM` 行 ——
它不会被"块边界切错"影响，所以能裁决 ① 与 ② 谁对。

**② 错的三个条目全部报 0**，而 0 看起来不像是"解析失败"，
像是"这个结构没有原子"。**这种错误不会自己喊出来。**

→ 实现者**必须**按 `loop_` 语义解析。这是 T3 判分器的第一个硬约束。

## 三、判分器计算什么（四个量，全部确定）

作答格式：**一个 JSON**，形如

```json
{"pdb_id": "1CRN",
 "atom_count": 327,
 "hetatm_count": 0,
 "chain_count": 1,
 "element_histogram": {"C": 0, "N": 0, "O": 0, "S": 0},
 "ca_distance": 0.0}
```

| # | 量 | 定义 | 为什么确定 |
|---|---|---|---|
| 1 | `atom_count` | `group_PDB == "ATOM"` 的行数 | 纯计数 |
| 2 | `hetatm_count` | `group_PDB == "HETATM"` 的行数 | 纯计数 |
| 3 | `chain_count` | `label_asym_id` 的去重数目 | 纯计数 |
| 4 | `element_histogram` | `type_symbol` 的直方图（**只统计 ATOM 行**，键为元素符号） | 纯计数 |
| 5 | `ca_distance` | 第一条链上**第 1 个与第 2 个** `CA` 原子之间的欧氏距离，单位 Å，**保留 3 位小数** | 由坐标算；见 §4 |

**为什么选这些量**：它们全部只依赖 `_atom_site` 的**离散字段**（计数）
或**一次坐标减法**（距离）—— 没有阈值、没有参考区间、没有外部定义。
**任何引入外部标准的量都被排除**（见 §6）。

## 四、确定性判据（这是 T3 的核心卖点）

**定义**：同一个 mmCIF 输入，在**任意**机器、任意次重复运行，
上述五个量必须**逐位相同**（数值按固定小数位格式化后比较）。

**满足确定性的理由**：
- 量 1–4 是整数计数，与浮点无关
- 量 5 是一次 `sqrt(dx²+dy²+dz²)`。坐标为十进制字符串 →
  解析为 IEEE-754 double 是**确定**的（Python `float()` 是正确舍入）；
  `math.sqrt` 在 IEEE-754 下**正确舍入**，故结果确定
- 输出前**四舍五入到固定小数位**（`round(x, 3)`），避免"末位差异"

**实现要求**：
1. 坐标解析只用 `float()`，**不得**用 `numpy`（不同版本/平台可能改变归约顺序）
2. **不得**用任何并行/多线程求和
3. 距离计算**不用** `math.dist`（其内部实现可能随版本变化）—— 显式写
   `math.sqrt(dx*dx + dy*dy + dz*dz)`
4. 输出比较时**先格式化**成固定小数位字符串再比

**必须在容器内实测的验证**（交给 verifier）：
同一镜像连跑 ≥3 次，逐位比较 `result.json`。

## 六、非目标（明确写出，避免范围蔓延）

- ❌ **不做结构预测**，不调用 AlphaFold / ESMFold / 任何模型
- ❌ **不引入第三方 Python 依赖**（保持零依赖；不用 numpy/biopython/Bio.PDB）
- ❌ **不依赖网络**（运行时）。mmCIF 预置在镜像里；取数只在构建/准备阶段
- ❌ **不做需要外部参考区间的量**：Ramachandran 离群率需要二面角参考分布，
  `_pdbx_validate_*` 是 wwPDB 自带的校验结论（引用它=引用他人判断，不是重算）
- ❌ **不用会缺的标量字段**（R-free 等，见 §2.3）
- ❌ 不改动 T1/T2 的任何文件

## 七、预算与体积

| 项 | 预算 | 依据 |
|---|---|---|
| 运行时间 | **秒级**（远低于 30 分钟） | 纯解析 + 一次坐标减法；实测取数 + 解析 1CRN 秒级 |
| 单条 mmCIF | 70 KB ~ 772 KB | §2.1 实测 |
| 题池体积 | 建议 **20–40 条 ≈ 5–15 MB** | 按中位 326 KB 估；超 40 条应重新评估仓库体积 |
| 峰值内存 | < 200 MB | 最大条目 5XNL 98,986 原子（约 8 MB 文本） |

**题池选择规则（写进取数脚本）**：
- 从 PDB 按**固定规则**抽样（例如按条目 ID 排序后取前 N 个满足条件的），
  **不挑选"好看的"** —— 与 `make_pilot.py` 的"不加挑选"原则一致
- 每个条目记 `sha256` 与取回时间，保证可复现
- 优先选**小体积**条目（< 400 KB），控制仓库体积

## 八、验收（实现者必须逐条做到；verifier 必须逐条独立验）

1. `tasks/T3/` 结构、`run.sh` 契约、`grade.py` 参数与 T1/T2 一致
2. 容器内 CPU-only 端到端跑通；对合成 oracle 作答得分为 **1.0**
3. 真值**全部由 mmCIF 确定性重算**；仓库里**不得出现手工填写的数值真值**
4. `grade.py --self-test` 存在，且**在判分器被破坏时会失败**（不能用恒真断言）
5. Dockerfile 构建期执行泄漏门禁；镜像内**不含** `truth.jsonl`
6. 取数脚本可重跑；`sha256` 记录在 `items.jsonl` 里
7. 接入 `record_image_digest.py` 与 `not_published.json`
8. 新增检查器都带 `--self-test`，且被 `run_all_checks.py` **实际调用**

## 九、仍不确定的地方（照实说，不许假装）

- ⚠️ **污染风险未定量**：PDB 条目 ID 与常见量（如 1CRN 的 327 个原子）
  可能已在 LLM 训练集中。这**削弱 T3 作为"能力评测"的价值**，
  但**不影响它作为"确定性/可复现性"的价值**。
  → 必须在 `DATACARD.md` 里写明这一限制，**不得**声称 T3 能测能力。
- ⚠️ **未验证**在 arm64 上的表现（本机 QEMU 模拟不可用）。
- ⚠️ 上述 8 个条目是**抽样**，不是全 PDB 统计；"字段存在率"只在这 8 个上成立。
  实现时应扩大到 ≥30 条再确认一次。
