# T3 —— 蛋白结构任务（mmCIF 确定性重算）

> **一句话**：给定 PDB 的 mmCIF 原文，从坐标**确定性地重算**一组结构量。
> 真值不是谁写的，而是**由原文算出来的** —— 任何人都能独立复算并推翻我们。

设计依据见 [`DESIGN.md`](DESIGN.md)；许可与数据来源见
[`../../research/T3_SOURCES.md`](../../research/T3_SOURCES.md)。

---

## 一、这道题考什么

20 个 PDB 条目，每题要求报告六个量：

| 量 | 定义 |
|---|---|
| `atom_count` | `group_PDB == "ATOM"` 的行数 |
| `hetatm_count` | `group_PDB == "HETATM"` 的行数 |
| `chain_count` | `label_asym_id` 去重后的数目 |
| `element_histogram` | ATOM 行的 `type_symbol` 直方图 |
| `model_count` | `pdbx_PDB_model_num` 去重后的数目 |
| `ca_distance` | 第一条链上前两个 `CA` 原子的欧氏距离（Å，3 位小数） |

这些量**全部只依赖 `_atom_site` 的离散字段或一次坐标减法** ——
没有阈值、没有参考区间、没有外部定义。所以它们是**确定的**。

> ### ⚠️ 计数口径：**统计全部 model**（这一条是修出来的）
>
> NMR 结构的 `_atom_site` 会列出**所有 model** 的原子，用
> `pdbx_PDB_model_num` 区分。而 RCSB 的 `deposited_atom_count` **只算一个 model**。
>
> **旧题面没规定算几个 model**，于是：
> - `1L2Y` 有 **38 个 model**：我们报 `atom_count=11,552`（全部 model 之和），
>   RCSB 报 **154**（单个 model）
> - 按常规理解（一个 model）作答的人**必然答错**，而且**无从知道**我们对齐哪种口径 ——
>   判定权在我们，他没得辩
>
> **修法**（审查 F3 → `t7`）：题面**明写**"统计全部 model"，并把 `model_count`
> 作为判分量报告出来 —— 口径从"隐藏约定"变成"可见事实"。
> 影响范围实测：题池 20 条中只有 `1L2Y` 是多 model 结构。

## 二、⚠️ 诚实说明：这题**不能**用来测"能力"

**必读**。理由有二，都不是谦虚：

1. **常见条目的数值可能已在 LLM 训练集中。**
   1CRN（Crambin）、4HHB（血红蛋白）是教科书级条目。
   我们**无法核实**训练集内容，所以不猜测、也不声称。
2. **真值可由原文重算** —— 这意味着"知道答案"和"会算"在这里几乎等价。

**所以 T3 主张的是**：

> ✅ 它测**能否按规范确定性地重算**，以及**过程是否可复现**。
> ❌ 它**不**测"模型理解蛋白结构"。

这一条必须同步写进 `docs/DATACARD.md`。**把它写在 README 里，而不是留给读者自己发现** ——
本项目的一贯做法是主动写清限制（见 `docs/DATACARD.md` §4）。

## 三、怎么跑

### 3.1 取数（只需一次；结果不进 git）

```bash
cd tasks/T3/data
python3 fetch_mmcif.py --outdir .       # 20 条 mmCIF → items.jsonl + truth.jsonl
python3 fetch_mmcif.py --outdir . --check   # 只核对，不下载
```

取数脚本**可重跑**，且每个条目的 mmCIF `sha256` 记录在 `items.jsonl` 里 ——
所以"拿到的到底是不是我们用的那一份"是可验证的。

### 3.2 在容器里跑

```bash
docker build -t veribench-bio/t3:dev tasks/T3

# 真值**只读挂载**（镜像里不含答案）
docker run --rm \
  -v "$PWD/tasks/T3/data/truth.jsonl:/data/truth.jsonl:ro" \
  -v "$PWD/out:/out" \
  veribench-bio/t3:dev
# → /out/result.json
```

被测系统把作答写到 `/out/answers.jsonl`（每行一个 JSON）。

### 3.3 判分器自检

```bash
python3 tasks/T3/grade.py --self-test
python3 tasks/T3/data/mmcif_parse.py --self-test
```

## 五、这道题实现时踩到的两个坑（都留了检查）

### 坑 1：mmCIF 必须按 `loop_` 语义解析，不能按 `#` 切块

`#` 在 mmCIF 里是**列名块与数据块之间的分隔符**，出现在数据**之前**。
按 `#` 切块会让 4HHB / 6LU7 / 2LZM 报 **0 个原子**（真实 4,384 / 2,387 / 1,309）——
而 **0 看起来像"这个结构没有原子"，不会自己喊出来**。

`mmcif_parse.cross_check_totals()` 就是为此存在：它用**不依赖解析结构**的
全文件计数做裁判，两者不一致就抛异常。

### 坑 2：浮点容差不能设在噪声量级上

第一版判分器用 `abs(got - want) <= 0.001` 比较距离。
实测 `abs(3.801 - 3.8) = 0.001000000000000334` —— **比 0.001 大 3.3e-16**，
于是"容差内的正确作答"被判错。

**根因不是容差小，而是 epsilon 恰好落在 IEEE-754 舍入噪声的量级上**，
边界由噪声决定。改成按契约 `round(got, 3) == round(want, 3)` ——
精确、无 epsilon、与契约一致。

> 这两个坑都来自**同一个经验**：`0` 和"看起来对"都可能掩盖错误。
> 所以两者的自检都**含负向用例**，而不是只测正常路径。

---

### 坑 3：判分器里**硬编码了"每题 5 个量"**

加 `model_count` 时才发现：`grade.py` 里写着 `n_metric += 5`。加一个判分量就会**静默算错总数** ——
而**错的总数看起来仍像个正常数字**（本项目反复踩的那一类）。

已改为由 `N_METRICS_PER_ITEM` 常量推导。**不写字面量**。

> 这三个坑都来自**同一个经验**：`0`、`5`、`0.001` 这种数字**看起来都对**，
> 所以错误不会自己喊出来。三处的自检都**含负向用例**，而不是只测正常路径。
