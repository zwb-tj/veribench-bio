# 亲手做一次「检查失败演练」

**为什么要做这件事**：一个只会说 ✅ 的检查器等于没有检查器。这个仓库里每个
扫描类检查器都带 `--self-test`（30 个），就是为了证明"它真的会失败"。但
`--self-test` 是**代码在证明自己**。这份文档是给**人**的：你自己动手弄坏一样东西，
亲眼看见它变红，再修回来。

做完你会得到一句能站得住的话：**"这些检查我见过它红，不是摆设。"**
这句话比再多 ✅ 都值钱 —— 面试里也只有这句话经得起追问。

---

## 准备：打开一个命令行窗口

1. 按 `Win` 键，输入 `cmd`，回车。
   会出现一个黑色窗口（命令行）。**下面所有命令都敲在这里。**
2. 先确认 Python 在：敲 `python --version` 回车。
   应打印 `Python 3.12.0`（或 3.10 以上任意版本）。
   若提示"不是内部或外部命令"，说明没装 Python —— 停下告诉我。

> ⚠️ 命令行里**粘贴**用鼠标右键（或 `Ctrl+V`），不要用 `Ctrl+C`（那是中断）。

## 进入项目目录

敲这一行，回车：

```
cd /d "D:\software\DeepSeek Harness\bio-eval"
```

（`/d` 是允许跨盘符切换。`cd /d "路径"` 里引号是必需的，因为路径可能有空格。）

---

## 第 1 步：先看它现在是绿的

```
python scripts\verify_readme.py
```

**预期看到**：最后两行是

```
共 13 条：通过 13 · 不符 0 · 无法验证 0
✅ README 的路径与关键断言均与工作区一致
```

记住这个"绿"的样子。这 13 条断言里，有 5 条是在核对 README 里那张目录树
和磁盘上的真实目录是否一致。
（⚠️ 如果这里看到的条数和我写的不一样，**以你屏幕上印的为准** —— 这个检查器
自己在长，写死的数字迟早会过期。这也是本项目记了几十条的教训之一。）

---

## 第 2 步：弄坏它（不用改任何文件内容）

这一步**只改一个文件夹的名字**，不动任何文件内容 —— 所以完全可逆、零风险。

打开文件资源管理器，进到：

```
D:\software\DeepSeek Harness\bio-eval\tasks
```

找到里面的 **`T4`** 文件夹，把它重命名（`F2` 或右键→重命名）为：

```
T4_backup
```

> 为什么这一步有效：README 的目录树里写着 `└── T4/`，意思是"仓库里有 T4 这个题目"。
> 你把文件夹改名之后，这个声明就变成假的了 —— 而 `README.md` 正文**一个字都没动**。
> 这正是"文档说的和事实不一致"这类缺陷的最小形态。

## 第 3 步：再看一眼

回到命令行，把第 1 步那条命令再敲一次：

```
python scripts\verify_readme.py
```

**预期看到**这 3 条从 ✅ 变成 ❌（其余 10 条仍是 ✅）：

```
目录树里列出的子项都真实存在                          ❌ 不符
                                        └ 树里有但仓库没有：['tasks/T4']
目录树列出的子项是完整的（没写省略号的目录）               ❌ 不符
                                        └ tasks/ 缺 ['T4_backup']
目录树列全了 tasks/ 下的题目（T1…TN）               ❌ 不符
                                        └ tasks/ 缺 ['T4_backup']

共 13 条：通过 10 · 不符 3 · 无法验证 0
❌ README 与实际不符 —— **改 README，不要改事实**。
```

**看到 `❌` 和 `不符 2`，这一步就成了。** 你刚刚亲眼看见：
- 检查器**真的会失败**，它不是一个永远说 OK 的摆设；
- 它失败的**理由是对的**（"README 里写了 T4，但磁盘上没有"）；
- 它甚至告诉你**该往哪边改**（`改 README，不要改事实` —— 因为这个仓库的规矩是
  以事实为准，文档要去迁就事实，而不是反过来）。

### 想再看一件事（可选，约 1 分钟）

在仍然弄坏的状态下敲：

```
python run_all_checks.py
```

**预期**：它会**把 54 步都跑完**（不是一遇到错就停 —— 它要把所有问题一次报全），
最后打印：

```
❌ 共 3 项失败
```

而且退出码变成非 0。这三项是同一件事在三个不同检查器里的三次报告：

```
❌ python.exe verify_readme.py   → ❌ README 与实际不符
❌ python.exe verify_doc_links.py → ❌ 文档里指向不存在的路径
❌ python.exe verify_t1_claims.py → ❌ T1 的文档断言与实际产物不符
```

**这本身就是这节课的重点**：一个坏掉的事实会被**多个互不共享假设的检查器**各自抓到一次。
如果你只看见 `verify_readme.py` 报错，那可能只是它过敏；三个不同来源都说同一个东西不存在，
那才是真的。**（对照：`README.md` 里从来没有 T3/T4 那一次，三个检查器全都没抓到 —— 详见 `SPEC.md` §3.1 第 56 条。）**

## 第 4 步：修回来

把 `T4_backup` 文件夹**改名回 `T4`**（名字必须一模一样）。

然后回命令行确认：

```
python scripts\verify_readme.py
```

**预期**：又变回

```
共 13 条：通过 13 · 不符 0 · 无法验证 0
✅ README 的路径与关键断言均与工作区一致
```

再敲这一行确认仓库回到了干净状态：

```
git status --porcelain
```

**预期**：**什么都不打印**（干净）。
若它列出了 `D tasks/T4/...` 之类，说明文件夹名字没改回 `T4` —— 回去改。

---

## ⚠️ 唯一需要当心的两件事

1. **在第 2 步弄坏、第 4 步修回之间，绝对不要 `git commit`、不要 `git push`。**
   那个窗口里 `T4` 是"已删除"状态，提交上去就等于把 T4 整段从仓库里删掉。
   只要你**不敲** `git commit` / `git push`，就不可能造成任何不可撤销的后果。
2. **必须改回原名 `T4`**，不是 `T4b`、不是 `T4_backup`。
   改完用 `git status --porcelain` 确认它**什么都不打印**。

---

## 一句话总结你刚才做的事

你先让检查器**绿**，再制造一个**只有你知道的**、真实的错误，确认它**变红且理由正确**，
最后**亲手**把它修回绿。

这就是这个项目的核心主张：**判据先于结论，而且判据必须能证伪自己。**
面试时如果有人问"你怎么知道你的检查是真的"，你答的不是"我写了很多检查"，
而是"**我弄坏过它，我看着它红的**"。

---

## 附：如果想换成命令行版本（不用鼠标）

上面第 2 步用资源管理器改名。等价的两条命令是：

```
ren tasks\T4 T4_backup      :: 弄坏
ren tasks\T4_backup T4      :: 修回
```

两条都跑一遍，效果与鼠标操作完全相同（`ren` = rename）。
